## 为什么选这篇，而不是收集一组提示词

Simon Willison 是 Django 的共同创建者、Datasette 的作者；身份可以在他的[个人介绍](https://simonwillison.net/about/)核对。这里选择这篇文章，是因为它把 AI 编程写成需要学习和判断的工作，而不是一次输入就结束的操作。

原文发表于 **2025 年 3 月 11 日**。本文只短摘其中两处文字，重点讨论准备输入与检查结果；其他段落是本站延伸。原文里的产品、模型和功能描述有当时的时间背景，不能直接当作今天的功能清单。

这份批注围绕一个问题展开：当工具替我们写出代码，开发者还应当掌握什么，才能接着维护它？下面借用本站筛选与笔记 API 的需求，构造可用于学习的情景。

## 短摘一：上下文为什么比一句指令更重要

### 本站批注：先交代系统现在怎样工作

“支持多个主题”这句话只说了目标，没有决定规则。选两个主题，是符合任一主题就出现，还是必须同时包含？已选日期、关键词和当前页怎么办？如果不写清楚，几种不同实现都可能看上去合理。

有效的任务材料应该让接手者看见**当前行为、目标行为和不能被破坏的约定**。文件再多，也不能代替这三件事。反过来，一份很短的材料如果包含这些约定，往往已经能排除许多错误方向。

下面是一份本站整理的任务材料模板，可以在开始修改之前填写。它不是原文摘录，也不是某个工具专用指令。

```text
问题：主题索引目前一次只能选一个。
目标：默认取多个主题的并集；再次点击取消。
已有条件：类型、关键词、日期、排序、页码。
保留规则：主题变化不清除类型、关键词与日期。
页码规则：条件改变后回第一页，再根据结果数量计算页数。
复现数据：一篇只有 DNS，一篇只有 Python，一篇同时有二者。
入口：归档页面、筛选脚本、文章标签数据。
验收：多选、取消、空结果、刷新和返回均保持约定。
```

这里最有用的材料不是“请写得专业”，而是三个可区分的样例。只测一篇同时带两个标签的文章，并集和交集都能给出相同结果，无法发现规则是否选错。

### 本站批注：给上下文设一个结束点

一次对话里出现过的错误尝试、过期接口和临时假设，很容易与最终规则混在一起。继续之前，可以重新整理一份“已经确认的事实”，并给出当前版本文件；把尚未确认的猜测单列出来。

这不是让工具记住更多，而是让输入更容易核对。不要把真实凭据、客户数据或整个私有数据库当作普通任务附件。用于解释问题的样例，保留必要结构和边界值即可。

### 本站批注：验证的是需求，而不只是工具的解释

“已经实现”“测试通过”“浏览器没有问题”，分别是什么证据？它们不能合成一句泛泛的完成说明。代码能构建，不能证明筛选规则正确；一个正常页面，也不能证明刷新、返回和失败恢复都正确。

先从需求写出预期，再观察运行结果。尤其不要只让同一个生成过程替自己的实现补一组断言：如果需求理解本来就偏了，代码和测试可能一起保持一致地犯错。

针对前面的主题筛选，下面是本站整理的验收设计。表里的结果是**预期**，不是运行报告。

| 操作 | 应观察的结果 | 它在区分什么 |
| --- | --- | --- |
| 选择 DNS，再选择 Python | 出现含任一标签的记录 | 并集与交集 |
| 再点一次 DNS | 只剩 Python 的条件 | 多选与取消 |
| 已选日期后增加主题 | 日期仍在，结果重新计算 | 条件叠加与整体重置 |
| 在第三页改变主题 | 新结果从第一页开始 | 页码是否过期 |
| 刷新一个带条件的网址 | 选择与列表一致 | 内存状态与可恢复状态 |
| 进入文章，再返回归档 | 恢复进入前的条件 | 导航是否丢失状态 |

如果要看已经附有可运行测试的独立样例，可对照[FastAPI 笔记接口](/blog/fastapi-from-zero/)：无效输入是否写入数据库、`false` 是否被 PATCH 保留、错误 Key 是否被拒绝，都是能观察的行为。那篇记录的测试范围不等于所有应用场景都已经覆盖。

### 本站批注：测试不应替开发者承担解释责任

通过的测试只是已覆盖场景的证据。接手代码的人还需要能解释：数据从哪里来，输入在哪一层受约束，失败后留下什么状态，改这里为什么可能影响另一处。

以任务创建为例，请求成功而列表仍旧，可能是查询缓存没有失效；重新加载又能看到数据，说明持久化与页面更新不是同一步。沿这条链理解，才能决定应检查接口、数据库还是缓存，而不是随机重复提交。具体职责可以继续读[TaskHub 技术栈笔记](/blog/taskhub-web-stack/)。

## 把这次阅读变成自己的工作记录

可以挑一个小功能，按下面四行记录一次练习，不要求一开始写成长文：

```text
我希望改变的行为：
我提供给工具的事实与约束：
我亲自观察的正常路径和失败路径：
我仍然解释不清、需要继续查证的地方：
```

最后一行尤其值得留下。它能区分“这次碰巧能用”和“以后还能维护”。如果某段实现暂时无法解释，就先缩小修改范围、补文档或重现样例，不急着给它贴上完成标签。

本文保留的阅读结论是：把输入整理清楚，把结果放回具体行为里检查。这个原则可以继续使用；原文列举的工具能力与版本，则需要每次回到当前资料核对。
