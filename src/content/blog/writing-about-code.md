## 一篇文章先回答一个主要问题

“项目采用现代技术栈，具有良好扩展性。”这句话几乎可以放进任何项目介绍。读者仍不知道系统解决了什么，也不知道下次遇到类似问题该怎么做。

[Diátaxis](https://diataxis.fr/)把技术文档分为教程、操作指南、参考和解释，对应不同的阅读需要。这里借用它对读者目的的区分，并不把本站四类手记硬套成四类文档。

同样讲博客搜索：带新手完成第一次筛选，是教程；告诉维护者如何增加条件，是操作指南；列出 URL 参数，是参考；讨论为什么把状态放进 URL，是解释。把任务混在一起，读者往往每一步都能看见一点，却无法顺利完成任何一件。

## 用具体行为替换抽象评价

试着把“搜索体验更完善”改成下面的说明：

> 用户按分类和关键词筛选后，条件写进网址；复制链接到新窗口，页面能恢复相同条件。从文章页返回时，也应保留进入前的筛选。

这段话出现了触发方式、状态和可观察结果。它能写进文章，也能指导验收。如果系统尚未实现恢复状态，就不能把它当作现有能力来写。

下面是针对本站场景整理的检查表：

| 要素 | 应该能回答的问题 |
| --- | --- |
| 场景 | 谁在什么情况下遇到问题？ |
| 动作 | 点了什么，或输入了什么？ |
| 规则 | 系统怎样理解并处理输入？ |
| 结果 | 用户能看到什么变化？ |
| 边界 | 哪些输入、环境或规模尚不支持？ |

## 解释选择，也记录代价

[ADR](https://adr.github.io/)用于记录重要架构决策。手记不一定需要正式流程，但可以借它留下选择发生时的上下文。下面是针对博客筛选的决策记录示例，不是额外功能的实现承诺：

```text
背景：少量公开文章，需要可分享的分类与关键词筛选。
选择：条件进入 URL，由浏览器筛选现有卡片。
备选：只放内存中；增加服务端检索接口。
代价：当前检索元数据，文章多时 DOM 与索引成本会增加。
重审条件：需要正文检索，或测出明显的输入响应延迟。
```

“为什么没有选另一个方案”通常比堆栈名称更有解释力。条件变化时，后来的人也能理解当时的选择，而不是把旧决定当成永久规则。

## 让证据与结论处在同一层

从代码看见 `loading="lazy"`，可以说图片启用了延迟加载；要说首屏快了多少，则需要设备、网络、页面版本和测量方法。一个截图只能证明一次可见结果，不能证明所有异常路径都正确。

我更愿意写成三种表达：“源码中可以确认……”说明静态事实；“按以下路径验证……”说明具体观察；“接下来需要测量……”留下未解决的问题。坦诚记录未验证部分，会让已经验证的结论更可信。

## 写完以后，删掉哪些句子

先删掉无法举例的形容词，例如“高性能”“高可用”“优雅”；再检查每个结论有没有例子或出处；最后让不熟悉项目的人只读标题和目录，看看能否猜到文章解决什么问题。

技术写作不要求每次都展示复杂实现。把一个小问题讲准确，把适用条件说完整，让读者知道如何验证，已经能体现工程判断。下一次复盘，可以从一个真实故障、一次选择或一个容易混淆的概念开始。
