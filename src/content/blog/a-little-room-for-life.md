## 为什么写完代码以后，任务还没有结束

一次常见的交付现场是：按钮能点，页面也没有明显报错，完成说明写着“已修复日期筛选”。但读者选择 10 月 1 日到 3 日时，3 日的文章没有出现；取消弹窗后，列表又变成了刚才未确认的范围。局部看起来可用，整体行为仍然错了。

这类问题在手工开发和 Coding Agent 协作中都会发生。代码生成速度变化以后，更需要把“需求是什么、结果如何确认、还缺什么证据”提前说清楚。本篇按一次完整的小型改动走到底，用日期筛选说明如何从模糊需求走到可以评审的交付。

这里的代码是独立教学实现，不替换本站日期组件；验收场景借用本站的归档需求。这样可以先把规则看清楚，再把它放回真实页面，避免把框架细节与业务问题混在一起。

## 第一步：把现象转成明确的契约

“优化日期筛选”无法直接验收。先写清输入、输出、边界和必须保留的状态：选择起止两天，结果包含首尾；同日范围只包含当天；取消不会改变已经应用的条件；清除日期保留关键词和类型；刷新链接恢复已应用范围；范围变化后从第一页展示。

还应决定异常输入如何处理。本文的纯规则层拒绝不存在的日期与反向范围；界面层可以在交给规则前归一化反向选择。两层职责不同，不要让一个地方自动交换，另一个地方静默返回空结果。

| 场景 | 正确结果 | 可能出现的错误 |
| --- | --- | --- |
| 10 月 1 日至 3 日 | 包含 1、2、3 日 | 错把结束日排除 |
| 开始与结束相同 | 包含当天记录 | 返回空集合 |
| 2 月 30 日 | 明确拒绝 | 被日期库归一化为 3 月 |
| 取消尚未应用的选择 | 原条件不变 | 草稿提前污染列表 |
| 第二页改日期 | 回到第一页 | 页码超出新结果范围 |
| 清除日期 | 类型和关键词仍在 | 所有条件一起被重置 |

这些句子先于实现存在，后面测试才有独立的判断标准。如果按代码分支倒着写一遍断言，测试很容易与错误实现保持一致。

## 第二步：沿数据流定位，不从截图猜原因

同一个症状可能来自不同层次。结束日没有文章，可能是比较符号错误，也可能是日期转换跨了时区，还可能是文章属于草稿。点击“取消”后状态变化，通常又是另一条路径。

先沿这条链检查：

```text
文章的发布日期
  → 归档中的日历日标识
  → 已应用的筛选条件
  → 弹窗内尚未确认的草稿
  → 匹配结果与分页
  → URL 写入、刷新恢复与返回链接
```

每一步都提出一个可回答的问题：数据确实有这一天吗？日期是时间点还是日历日？列表使用的是 applied 还是 draft？重新计算后页码是否仍有效？URL 的读写格式是否相同？

这比一次性改遍所有函数更容易定位。可以先构造一篇明确位于结束日的样例，再观察它在哪一层消失。调试是缩小不确定性的过程，不是不断增加补丁数量。

### 日期究竟表示什么

“2026-10-03”在这个业务里表示一个日历日；“2026-10-03T00:30:00Z”表示一个时间点。二者不能随意互换。如果文章记录时间戳，应先按站点约定时区转换成日历日，再做日期范围比较。

[MDN 的 Date 文档](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date)区分本地和 UTC 的日期解释。本文为了专注日历规则，限定输入为有效且补零的 `YYYY-MM-DD`。在这个前提下，字符串顺序才与日期顺序一致。`2026-2-3` 不能混入同一比较规则。

## 第三步：先实现可以独立验证的规则

下面的例子只依赖现代 Node.js 内置模块。新建一个 `date-range.mjs` 文件，把下一节的测试也放在同一文件中，最后执行 `node date-range.mjs`。它不需要安装测试框架，也不需要启动网页。

```js
import assert from 'node:assert/strict';

function validDay(value) {
  if (typeof value !== 'string' || !/^\d{4}-\d{2}-\d{2}$/.test(value)) {
    return false;
  }
  const date = new Date(`${value}T00:00:00.000Z`);
  return !Number.isNaN(date.valueOf()) &&
    date.toISOString().slice(0, 10) === value;
}

function inRange(day, from, to) {
  if (![day, from, to].every(validDay)) {
    throw new TypeError('Expected a real date in YYYY-MM-DD format');
  }
  if (from > to) throw new RangeError('Start must not follow end');
  return day >= from && day <= to;
}

function filterNotes(notes, from, to) {
  return notes.filter(note => inRange(note.day, from, to));
}
```

这里有三处值得解释。首先，正则只检查形状，不能识别 2 月 30 日，所以还要转换后回查原值。其次，比较明确使用 `>=` 与 `<=`，表达包含首尾。最后，函数不访问页面、URL 或本地时间，让规则可以单独运行。

`filterNotes` 是教学边界，不是完整内容校验器；它假定每条记录有 `day` 字段，且元数据已在输入层校验。空数组的范围检查也不在这个函数中完成。如果要公开成通用接口，应先统一检查范围，再处理记录，并为缺失字段定义错误信息。把前提写清楚比假装函数可以处理所有输入更有帮助。

## 第四步：写能揭露错误实现的反例

把以下内容接在同一文件的规则代码之后：

```js
const notes = [
  { id: 'before', day: '2026-09-30' },
  { id: 'start', day: '2026-10-01' },
  { id: 'middle', day: '2026-10-02' },
  { id: 'end', day: '2026-10-03' },
  { id: 'after', day: '2026-10-04' },
];
const ids = filterNotes(notes, '2026-10-01', '2026-10-03')
  .map(note => note.id);
assert.deepEqual(ids, ['start', 'middle', 'end']);
assert.equal(inRange('2026-10-03', '2026-10-03', '2026-10-03'), true);
assert.equal(inRange('2026-09-30', '2026-09-29', '2026-10-01'), true);
assert.equal(validDay('2024-02-29'), true);
assert.equal(validDay('2025-02-29'), false);
assert.equal(validDay('2026-02-30'), false);
assert.equal(validDay('2026-2-03'), false);
assert.throws(() => inRange('2026-02-30', '2026-02-01', '2026-03-01'), TypeError);
assert.throws(() => inRange('2026-10-02', '2026-10-03', '2026-10-01'), RangeError);
assert.deepEqual(notes.map(note => note.id), ['before', 'start', 'middle', 'end', 'after']);
console.log('Date range checks passed');
```

运行后应输出 `Date range checks passed`；任何断言失败都会使进程报错。这里选择了首尾、同日、跨月、闰年、不存在的日期、格式和反向范围，而不是只测十个普通日期。

还可以做一个很小的“错误注入”实验：把实现中的 `day <= to` 临时改成 `day < to`，重新运行，第一组断言应失败；恢复代码，再确认通过。如果测试对这个改动毫无反应，它就没有验证我们最在意的结束日问题。这个实验说明测试是否有辨别力，不建议把故意错误留在提交中。

[Node 的 assert 文档](https://nodejs.org/api/assert.html)提供断言接口。框架名字不是这里的重点，重点是测试输入来自业务边界，预期结果能独立于实现写出来。

## 第五步：接回页面时，分开草稿与已应用状态

纯函数正确，还不能保证界面正确。日期弹窗需要两个阶段：读者正在选择时，可以调整和取消；确认以后，才改变列表。一个清楚的状态结构是：

```text
applied = { from, to }   当前列表正在使用的范围
pending = { from, to }   弹窗中尚未确认的范围

打开弹窗：pending = copy(applied)
选择日期：只修改 pending
点击应用：校验 pending → applied = copy(pending) → page = 1
取消 / Escape / 遮罩：关闭弹窗，丢弃 pending
清除日期：只清空 applied.from、applied.to → page = 1
```

这是状态转换说明，不是可直接粘贴的组件代码。关键在于对象不要共享一个可被原地修改的引用，否则“只修改草稿”可能仍然改变已应用值。

URL 也只保存已应用状态。临时点了一个日期又取消，不应改变地址栏。刷新时先解析并校验参数，再计算筛选与分页；不能先显示第二页，再用异步初始化偷偷重置条件。

对于不同入口，也需要一致约定：点击日历中的某一天是立即应用；在自定义弹窗里选择日期需要确认；“清除日期”只移除日期。控件可以有不同交互形式，但最终要进入同一条状态更新路径。

## 第六步：在浏览器里验收完整操作

规则测试无法判断按钮被遮住、焦点丢失或手机出现整页横向滚动。浏览器检查应围绕用户路径，而不是只打开页面截一张图。

一次有针对性的操作顺序是：先带着关键词和类型打开第二页；选择起止日期并应用，确认页码回到一；再次打开弹窗修改范围，按 Escape，确认结果未改变；清除日期，确认关键词与类型仍然存在；复制地址并刷新，确认条件恢复；进入文章再返回，确认查询参数保留。

接着用键盘和窄屏重复关键步骤。键盘至少检查触发按钮、日期选择、应用和取消能否到达，关闭后焦点是否返回合理位置；手机检查弹窗在可视范围内、底部操作可触达，代码和表格只在各自容器中横向滚动。

| 证据 | 能支持的结论 | 不能单独支持的结论 |
| --- | --- | --- |
| 规则断言通过 | 覆盖到的日期规则正确 | 弹窗草稿状态正确 |
| 构建成功 | 本次生成与打包未被阻断 | 所有交互都正确 |
| 桌面截图 | 该尺寸与状态的视觉布局 | 手机、键盘和刷新行为 |
| 完整点击记录 | 这条用户路径符合预期 | 所有浏览器、所有输入 |

测试数量本身不是交付质量。挑选会改变结果的边界，并清楚说明覆盖范围，比堆很多与实现同构的断言更有用。

## 第七步：评审先看行为，再看复杂度

[Google 的代码评审指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)把设计、功能、复杂度与测试都纳入检查。对这次任务，可以按三个问题来读补丁：是否解决了约定行为；是否引入了不需要的新机制；是否给出了对应的运行证据。

先看修改涉及的路径。日期筛选合理地会影响状态处理、列表结果和 URL；若同时更换全站字体、重写导航并新增一套状态库，就应要求解释它们与目标的关系。范围越宽，行为变化越难归因，回退也越困难。

再看规则是否只有一个来源。若日期按钮、搜索框和页码各自复制一份筛选逻辑，即使今天都通过，下一次修改仍容易产生分歧。应让它们更新状态后进入共享计算路径，而不是从每个事件里重新拼一遍结果。

最后看异常分支。没有结果是正常业务状态，格式错误是输入问题，工具未运行是验证缺失，三者不应都包装成“成功”。Agent 的完成说明尤其需要与实际返回值核对：检查启动了，不代表运行结束；补丁请求发出，也不代表应用成功。

## 第八步：写一份别人可以接着工作的交付说明

交付记录可以很短，但要覆盖目标、变更、证据和限制。例如下面是一份格式示例，其中结果需要用本次真实记录替换：

```text
目标：修复范围结束日遗漏，并保留原有筛选状态。
变更：统一日历日校验与包含首尾的比较；分离弹窗草稿和已应用值。
验证：日期反例检查通过；完成应用、取消、清除、刷新和返回路径。
视觉：检查桌面与手机；表格和代码不撑宽页面。
限制：尚未验证的浏览器或时区环境，逐项列明。
```

没有执行的项目就写未执行，不把预期结果写成实测结论。链接到相关文件和检查输出，可以使评审者从说明快速定位到证据。小范围且可以独立理解的修改也符合 [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)倡导的评审方式。

如果上线后出现问题，先确认可回退的版本和内容状态，再调查原因；不要在证据不足时连续叠加修复。个人项目也值得保留一个明确的可用基线，它降低的是下一次修改的心理与技术成本。

## 留下方法，也留下下一次能用的材料

一篇实践记录要比“今天修好了一个 bug”多走一步：把最初现象、真正原因、关键选择和能揭露错误的输入留下来。下一次遇到类似问题，读者才知道应该先检查哪一层，而不是重复猜测。

这次日期案例最终沉淀的是一套顺序：定义行为 → 定位数据流 → 分离可测规则 → 用反例验证 → 接回真实交互 → 根据证据评审与交付。Coding Agent 可以承担其中大量阅读、修改与重复操作，但判断标准仍需要被明确表达。
