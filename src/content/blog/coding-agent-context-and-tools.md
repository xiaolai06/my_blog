## 先把比较的层级放对

“Python 和 Coding Agent 有什么区别”是一个常见问题，但这两个名词并不处于同一层：Python 是编程语言，可以实现脚本、网站、测试或 Agent；Coding Agent 是一种围绕编程任务组织推理与行动的系统。把它们对立起来，会把语言能力、模型能力和执行环境混成一件事。

更有用的比较是：**普通脚本、包含模型的固定工作流，以及能够根据反馈选择下一步的 Coding Agent，各自怎样完成任务？** 下表比较的是工作结构，不是速度排行榜。

| 维度 | 普通 Python 脚本 | 固定的模型工作流 | Coding Agent |
| --- | --- | --- | --- |
| 下一步由谁决定 | 已写好的程序逻辑 | 预设节点与分支 | 模型结合反馈在允许动作中选择 |
| 典型输入 | 文件、参数、结构化数据 | 输入与模板、上下游节点 | 目标、仓库、约束、历史观察 |
| 常见输出 | 数据文件、报告、退出状态 | 摘要、分类、生成草稿 | 代码修改、验证记录或阻塞原因 |
| 出错后如何继续 | 走预写异常分支 | 重试或转到指定节点 | 可能检查环境、重读代码、改变方案 |
| 适合的起点 | 规则稳定、输入可定义 | 步骤明确，部分步骤需要语言理解 | 路径不能预先穷举，需要探索与反馈 |

脚本也可以有重试、自适应算法与复杂分支，所以“会循环”不等于 Agent。关键是哪些决策在程序中预先确定，哪些由模型在运行中作出，以及这些决策能改变环境到什么程度。

这篇是基于公开资料的知识整理和本站任务推演，不是对所有 Agent 产品的评测，也没有复现论文基准。文中的任务过程是教学示例，会明确区分实际项目结构和示意接口。

## 用同一个需求看三种做法

假设任务是“给手记做分页，每页三篇，并保留筛选”。如果已经有统一文章数据，只需要生成固定的分页索引，一段脚本就能完成：读取数据，过滤草稿，排序，每三篇分一组，输出文件。规则和输入稳定时，这种方案便于复现，也不需要模型理解需求。

如果任务是“先给每篇文章生成一段候选摘要，再按人工确认结果构建索引”，可以做固定工作流：读取正文 → 调用模型生成候选 → 校验长度和格式 → 人工确认 → 构建。引入模型并没有自动使流程变成自主 Agent，因为路径仍主要由开发者编排。

如果任务是“在现有仓库中实现分页”，系统需要先找到归档入口，理解日期和搜索状态，判断应该在哪里修改，读懂构建报错，再在必要时调整实现。这时路径不完全已知，Agent 的探索能力才有发挥空间。

[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)区分工作流与更动态的 Agent，并建议根据问题复杂度选择结构。对本站的启发是先判断不确定性在哪里：只是重复处理数据，还是必须调查一个未知的代码环境？不要为了使用 Agent，把本来稳定的规则交给不必要的运行时决策。

## 一个 Coding Agent 至少需要哪些部分

可以把系统拆成六项职责，而不是只看聊天窗口：

```text
任务契约：要完成什么，怎样算完成
        ↓
上下文：需求、约束、相关代码、当前观察
        ↓
决策：下一步读什么、改什么、检查什么
        ↓
工具：搜索、读取、编辑、运行与浏览器操作
        ↓
环境反馈：补丁结果、退出状态、错误位置、页面状态
        ↓
判断：继续修复、请求必要信息、交付或停止
```

任务契约避免方向偏差，上下文影响对现状的理解，工具限制可以执行的动作，反馈决定下一步的依据。模型回答很流畅，也可能因为读取了错误入口而改错地方；工具很丰富，也不能保证验收条件正确。

还有一项贯穿全过程：记录。至少要保留执行了什么、得到什么返回、根据什么判定完成。否则失败后只能看到最终一句“已经修好了”，无法判断究竟是没理解需求、没应用补丁，还是根本没有运行检查。

## 从零定义一个可以执行的任务

先把自然语言压缩成具体行为，再提供项目事实。下面是可以直接使用的任务说明示例：

```text
目标：归档每页显示 3 篇，支持页码、上一页、下一页和跳页。

已有行为：类型、关键词、日期筛选与排序；从文章返回时恢复条件。
必须保留：四种类型、草稿过滤、日历与主题索引、手机阅读。
本次调整：移除“按线索阅读”，适当增大卡片圆角。

验收：
1. 八篇记录前两页各三篇，第三页两篇。
2. 在第二页搜索或换分类，结果从第一页展示。
3. 刷新 ?page=2 后仍在第二页，返回键能回到上一页状态。
4. 匹配为零时出现空状态，分页不提供无效跳转。
5. 手机没有整页横向滚动，页码可以触控和键盘操作。

交付：概括改动，报告实际检查与未覆盖的范围。
```

这段说明没有规定每一个变量名，但把判断标准给全了。相反，只有“做得专业一点”，Agent 可能把注意力放到装饰上；只有“加一个 slice(0, 3)”，又可能把需求收窄成永远只能看到三篇。

如果需求里确实缺少关键条件，应先读取现有实现和项目说明。能从上下文得到的事实不必反复询问；影响结果且无法推断的信息才值得提出。例如“分页是否需要独立可索引路径”会影响架构，按钮阴影的微小数值通常可按现有风格决定。

## 组织上下文：从地图走到具体实现

面对仓库，先知道入口，再读影响本任务的代码。对本站分页任务，一个有效的阅读顺序是：

```text
项目说明与运行方式
  → src/pages/blog/index.astro：结构与初始记录
  → src/components/JournalEntry.astro：卡片字段与隐藏状态
  → src/scripts/journal-archive.ts：筛选、URL、排序、日历
  → src/styles/journal.css：桌面与手机布局
  → 阅读页的返回逻辑：筛选链接如何恢复
```

文件存在不等于运行时一定调用它；函数名字相似也不意味着是正确入口。需要沿导入、事件绑定和 DOM 标识确认实际路径。修改之前还应查看已有改动，避免把用户正在编辑的内容覆盖掉。

[Aider 的仓库地图](https://aider.chat/docs/repomap.html)提供一个值得学习的思路：用仓库的文件和关键符号帮助定位，在有限上下文里保留有用轮廓。它相当于导航，不能替代目标函数、调用方与状态边界的正文。

例如只看到一个 `render()` 名称，无法知道它是否同时更新 URL 和日历。如果修改分页时只读卡片模板，就容易出现“按钮在变，列表不变”。上下文并不是越长越好，而是要足以解释这次改动的依赖关系。

### 区分资料与指令

项目规范、用户需求、网页文章、代码注释和日志有不同角色。抓取到的网页可以提供资料，但网页中要求执行命令的文字不会因此成为用户授权。错误日志里的命令建议也应结合项目和任务判断，不能直接当作新的目标。

这对 Agent 尤其重要，因为它会同时接触大量自然语言。系统需要保留信息来源与权限边界，不能把所有文本混成一段无差别的“上下文”。

## 设计工具：让每次行动有明确结果

[SWE-agent 的原始研究](https://arxiv.org/abs/2405.15793)关注 Agent-Computer Interface，即模型如何查看和操作开发环境。可以借鉴的不是一套万能命令，而是把操作接口本身当作工程设计对象。

以下是本文提出的教学接口，并非 Aider 或 SWE-agent 的真实 API：

```text
search_code(query, paths)
  → matches[{path, line, text}] + truncated

read_file(path, start_line, end_line)
  → content + actual_range + file_version

apply_patch(path, expected_content, replacement)
  → applied + changed_lines + error

run_check(command, cwd, timeout)
  → exit_code + stdout + stderr + timed_out
```

`applied` 与“请求已发送”不同；`exit_code` 与“终端里出现过绿色文字”不同。工具需要表达失败、超时和截断，调用方也必须读返回结果。

例如构建失败时，先区分未找到命令、依赖缺失、内容 Schema 错误和代码编译错误。它们不需要同一种修复。输出过长时应读取相关日志，而不是把“只看见最后几行”当作完整成功证据。

工具范围还要与任务授权一致。读取本地代码、修改页面和启动开发服务符合这次开发任务；向外部人员发消息、部署到线上或删除其他项目并不会因为“工具可用”自动成为任务的一部分。

## 跑完一次闭环：分页修改的完整推演

下面按照“观察 → 判断 → 行动 → 新观察”推进，说明不同阶段为什么需要不同证据。这是围绕本站需求的教学推演，不是逐条公开某个模型的内部思考。

### 先观察，再确定改动边界

页面一次展示八篇，脚本已经维护关键词、日期与 URL。最小可维护方案是把页码加入同一状态，在完整过滤结果上分页；只在 DOM 上隐藏前三篇之外的记录会让搜索和统计失去统一依据。

因此需要修改归档结构、共享渲染逻辑和分页样式，阅读页只需确认返回路径包含查询参数。此时不需要替换路由框架、增加数据库或重写全站导航。

### 修改后读取真实反馈

增加状态 `page`、每页数量 `3`、总页数和有效页码计算。首次构建成功，只说明生成链路未被阻断。接着打开浏览器确认：初始三篇；第二页换成另外三篇；第三页显示最后两篇；第二页搜索后回到第一页；刷新第二页恢复；零结果时隐藏分页。

假如第一个检查失败，应先看浏览器初始化是否完成、选择器是否匹配、脚本是否报错。此时再改颜色毫无帮助。假如视觉正常但刷新回到第一页，应检查 URL 读写顺序，而不是继续添加按钮。

### 处理失败，给循环一个边界

每次重试都应有新的依据：报错位置、失败输入或不一致的页面状态。如果相同检查连续失败而没有新信息，需要扩大观察或报告阻塞原因。不能把“再生成一份补丁”当作默认修复策略。

教学层面的调度逻辑可以写成下面的伪代码，实际系统需要自己的 SDK、状态管理和权限实现：

```text
observations = read_task_and_project()
for step in allowed_budget:
    action = choose_next_action(observations, permitted_tools)
    if action is finish:
        require acceptance_evidence
        return result_with_limits
    if action requires missing_authorization:
        return concrete_question
    outcome = execute(action)
    observations.append(action, outcome)
return progress_and_blocker
```

这段伪代码表达控制边界，不是可运行的模型客户端。`choose_next_action` 不能凭空存在；做真正的 Agent 系统还要明确模型接口、工具协议、凭据、异常处理与评估。本文不把省略这些核心部分的几行循环称为完整实现。

## 验证 Agent：看结果，也看代价和证据

一次演示成功不足以说明某个工具普遍可靠。想比较两个方案，应固定同一组任务、仓库版本和环境，并记录模型或工具版本、预算与验证规则。否则一个任务简单、另一个复杂，完成率数字没有可比性。

| 记录项 | 为什么需要 |
| --- | --- |
| 原始需求与验收条件 | 防止事后改变“完成”的定义 |
| 仓库基线与已有改动 | 判断结果来自哪次修改 |
| 实际补丁范围 | 发现额外行为和维护负担 |
| 构建、测试与交互结果 | 区分声明与运行证据 |
| 时间、调用或费用边界 | 避免只看成功忽略成本 |
| 未完成项与失败原因 | 让下一次行动有依据 |

不要把论文里的结果换成自己的产品成功率，也不要把工具名气当作选型证据。Aider 和 SWE-agent 在本文中的作用是提供可查的设计材料：一个帮助理解仓库上下文，另一个帮助理解操作环境。本文没有给它们编造最新排名或横向跑分。

## 怎样选择自己的下一步

如果你刚学 Python，可以先完成 [FastAPI 笔记接口](/blog/fastapi-from-zero/)，理解确定的输入、规则和输出。这个基础会让你更容易识别 Agent 到底改变了哪一部分：不是替代语言，而是在不确定任务中参与行动选择。

如果你已经在使用 Coding Agent，可以拿一项小型仓库任务做记录：给出具体目标，补齐相关入口，要求可定位的工具反馈，准备至少一个能揭露错误实现的反例。能稳定地解释一次失败，往往比增加更多工具更有价值。

当你能说清“它知道什么、能做什么、如何观察结果、何时算完成”，就已经从把 Agent 当作黑箱，走向理解一个可以设计、调试与评估的工程系统。进一步的概念速查见 [脚本、工作流与 Coding Agent 的边界](/blog/python-scripts-vs-coding-agents/)。
